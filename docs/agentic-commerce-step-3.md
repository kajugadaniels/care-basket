# CareBasket Shopping Guide — Step 3 Controlled Orchestration

**Status:** Internal orchestration implemented; no model function calling enabled  
**Depends on:** [Step 1 agent contract](agentic-commerce-step-1.md) and [Step 2 catalog capabilities](agentic-commerce-step-2.md)  
**Implementation:** [`shopping-guide-orchestrator.ts`](../src/features/assistant/server/shopping-guide-orchestrator.ts)

## Purpose

Step 3 adds one deterministic coordinator between CareBasket application code and the price-free catalog capabilities. It accepts one strict, application-selected operation and returns either a product proposal or one server-written clarification question.

This layer complements the existing natural-language interpretation service. It does not replace Gemini grounding, deterministic keyword matching, private review persistence, or requester confirmation.

## Supported operations

| Operation | Capability | Result |
| --- | --- | --- |
| `SEARCH` | Bounded approved-catalog search | A proposal with 0–12 products, pagination availability, and the original phrase when no match exists |
| `PRODUCT` | One approved product lookup | A one-product proposal |
| `COMPARE` | Two-to-four product comparison | Exactly one clarification with server-owned copy and approved product options |

The operation kind is selected by trusted application code, not generated by Gemini. Zod rejects unknown kinds, ownership identifiers, extra fields, duplicate SKUs, and unbounded inputs before any capability runs.

## Safety and human control

- Results are proposals only. They do not change the client draft, save a request, notify a manager, or touch checkout.
- Search language remains inert data. Text that resembles instructions cannot select another operation.
- Missing search matches preserve the normalized requester phrase in `unresolved`; the orchestrator never invents a replacement product.
- Comparison text comes from CareBasket copy, while product names, images, categories, and sizes come from the approved catalog.
- Product failures remain generic catalog failures; the coordinator does not silently substitute or fall through to another capability.
- The coordinator requires Step 1 proposal authority, and every Step 2 capability still requires its narrower read authority.
- No prices, personal history, names, family details, payment data, or provider-generated labels enter the result.

## Deliberately deferred

Step 3 does not expose a Route Handler or Server Action, allow autonomous tool selection, or connect results to draft mutation. The next approved step should integrate this coordinator into requester-facing guidance while preserving an explicit requester click for every draft change and keeping Gemini schema-only and tool-free.
